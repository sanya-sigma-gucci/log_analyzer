# Анализатор журналов событий

Потоковый CLI-анализатор больших журналов событий. Читает файл **построчно**, не загружая его
целиком в память; фильтрует записи по временному интервалу, уровню и источнику; строит сводки;
сохраняет отчёт в JSON или CSV.

Формат строки журнала (разделитель `|` **запрещён** внутри полей):

```
2026-09-01T00:08:59Z | WARN | auth-api | AUTH_LOGIN_OK | User session created
```

* `timestamp` — ISO 8601 **UTC** (обязательно `Z` либо `+00:00` / `-00:00`; ненулевое смещение отклоняется);
* `level` — одно из `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`;
* `source`, `eventCode`, `message` — непустые строки без `|`.

---

## 1. Бизнес-требования

Службе поддержки нужно быстро находить частые ошибки и их источники в журналах нескольких
компонентов. Приложение должно:

* не хранить весь файл в памяти (только потоковая обработка);
* принимать путь к файлу и параметры через CLI;
* фильтровать по временному интервалу (`from` включительно, `to` исключительно), уровню и источнику;
* считать корректные и ошибочные строки, количество событий после фильтрации;
* строить сводки по уровням, по источникам и top-N кодов ошибок (события уровня `ERROR`);
* выводить сводку в терминал и опционально сохранять JSON / CSV;
* для каждой повреждённой строки показывать её номер;
* корректно обрабатывать пустой и отсутствующий файл;
* давать детерминированный (воспроизводимый) результат.

## 2. Реализованный функционал

### CLI-параметры

| Флаг | По умолчанию | Описание |
|------|--------------|----------|
| `-i, --input` | — | Путь к файлу журнала (**обязательно**) |
| `--from` | — | Начало интервала, ISO-8601 UTC, включительно |
| `--to` | — | Конец интервала, ISO-8601 UTC, исключительно |
| `--level` | — | `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR` |
| `--source` | — | Точное совпадение источника |
| `-n, --top` | `10` | Сколько top-N кодов ошибок показать (`0` — все) |
| `--format` | `json` | `json` или `csv` |
| `-o, --output` | — | Путь к файлу отчёта (если не задан — файл не пишется) |

### Что считается в сводке

* `total_lines` — всего строк в файле;
* `valid_lines` / `invalid_lines` — корректные / повреждённые строки;
* `filtered_events` — количество **корректных** записей, прошедших фильтр;
* `by_level`, `by_source`, `top_error_codes` — считаются **по отфильтрованным** записям;
* `parse_errors` — список повреждённых строк с номером, причиной и исходным содержимым.

### Коды возврата

| Код | Значение |
|-----|----------|
| 0 | Успех |
| 2 | Файл не найден / не читается / неверные аргументы |
| 3 | Не удаётся записать файл отчёта |

### Детерминированность

* `by_level` и `by_source` — сортировка по ключу;
* `top_error_codes` — сортировка по `(-count, code)` (при равенстве — по алфавиту);
* `parse_errors` — сортировка по номеру строки.

При повторном запуске на том же файле JSON/CSV получаются байт-в-байт идентичными.

### Эндпоинты

Не применимо — это CLI-приложение, HTTP-сервера нет.

## 3. Структура проекта

```
log_analyzer_project/
├── log_analyzer/
│   ├── __init__.py          # версия пакета
│   ├── __main__.py          # `python -m log_analyzer`
│   ├── parser.py            # строка → LogEntry / ParseError
│   ├── filters.py           # LogFilter.matches(entry)
│   ├── aggregator.py        # Summary и детерминированная финализация
│   ├── analyzer.py          # потоковая оркестрация: parse → filter → aggregate
│   ├── output.py            # вывод в терминал, JSON, CSV
│   └── cli.py               # argparse, коды возврата
├── tests/                   # pytest, ~80 тестов
│   ├── conftest.py
│   ├── test_parser.py
│   ├── test_filters.py
│   ├── test_aggregator.py
│   ├── test_analyzer.py
│   ├── test_output.py
│   └── test_cli.py
├── sample_data/
│   └── logs_events_sample.log   # демо-журнал с намеренно повреждёнными строками
├── analyze.py               # точка входа-обёртка
├── requirements.txt         # зависимости тестовой части
├── pyproject.toml
├── .coveragerc
├── run_tests.bat            # тесты + HTML-отчёты одной командой (Windows)
└── Readme.md
```

### Разделение ответственности

| Файл | Ответственность |
|------|-----------------|
| `parser.py`     | Разбор строки, валидация полей, парсинг UTC-времени |
| `filters.py`    | Проверка «подходит ли запись под фильтр» |
| `aggregator.py` | `Summary` + детерминированная сортировка |
| `analyzer.py`   | Потоковый цикл, связывающий парсер, фильтр и агрегатор |
| `output.py`     | Печать в терминал, сериализация в JSON/CSV |
| `cli.py`        | Парсинг argv, обработка ошибок, коды возврата |

## 4. Развёртывание

Требуется **Python 3.9+** на Windows 10 / 11.

```bat
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Сам анализатор **не имеет runtime-зависимостей** — в `requirements.txt` только стек тестов
(`pytest`, `pytest-cov`, `pytest-html`).

## 5. Запуск

Из корня проекта:

```bat
python -m log_analyzer --input sample_data\logs_events_sample.log
```

или эквивалентно:

```bat
python analyze.py --input sample_data\logs_events_sample.log
```

### Примеры (минимум три, как требуется)

#### Пример 1 — полная сводка по демо-журналу

```bat
python -m log_analyzer --input sample_data\logs_events_sample.log
```

Выводит в терминал общие счётчики, разбивку по уровням и источникам, top-10 кодов ошибок,
первые 50 повреждённых строк.

#### Пример 2 — ERROR-события `payment-worker` за первые 12 часов, отчёт в JSON

```bat
python -m log_analyzer `
    --input sample_data\logs_events_sample.log `
    --from 2026-09-01T00:00:00Z `
    --to 2026-09-01T12:00:00Z `
    --level ERROR `
    --source payment-worker `
    --top 3 `
    --format json `
    --output report.json
```

#### Пример 3 — top-5 кодов ошибок за весь журнал, отчёт в CSV

```bat
python -m log_analyzer `
    --input sample_data\logs_events_sample.log `
    --level ERROR `
    --top 5 `
    --format csv `
    --output report.csv
```

#### Пример 4 — проверка границ интервала (`from == to` → пустая выборка)

```bat
python -m log_analyzer `
    --input sample_data\logs_events_sample.log `
    --from 2026-09-01T06:00:00Z `
    --to 2026-09-01T06:00:00Z
```

`--from` включается в интервал, `--to` — нет, поэтому при `from == to` выборка пуста.

## 6. Тестирование

Одной командой (Windows):

```bat
run_tests.bat
```

Что делает скрипт:

```bat
python -m pytest tests `
    --cov=log_analyzer `
    --cov-config=.coveragerc `
    --cov-report=html:htmlcov `
    --cov-report=term-missing `
    --cov-fail-under=80 `
    --html=test-report.html `
    --self-contained-html
```

После запуска открываются:

* **HTML-отчёт по тестам:** `test-report.html`
* **HTML-отчёт по покрытию:** `htmlcov\index.html`

**Метрика покрытия:** построчное покрытие пакета `log_analyzer`
(`--cov-fail-under=80` роняет прогон, если покрытие < 80 %).

### Что исключено из покрытия

* `log_analyzer/__main__.py` и `analyze.py` — чистые точки входа (`if __name__ == "__main__"`).
* Внутри пакета — блоки `if __name__ == "__main__":` и `raise NotImplementedError`
  (объявлены в `.coveragerc`).

### Что проверяют тесты

* Корректные и повреждённые строки, пустые / пробельные строки, CRLF-окончания.
* Неверный формат даты, несуществующий месяц, отсутствие UTC-суффикса, ненулевое смещение,
  неверный уровень.
* Пустые `timestamp`, `level`, `source`, `eventCode`, `message` — по отдельности.
* `|` внутри `message` → ошибка «неверное число полей».
* Пустой файл, отсутствующий файл, каталог вместо файла.
* Границы `--from` (включительно) и `--to` (исключительно), пустое окно, комбинации фильтров.
* `--top` (ограничение), `--top 0` (все), отрицательный `--top` (отклоняется).
* JSON и CSV, вывод в терминал, диспетчеризация `--format`.
* Файл только из повреждённых строк, синтетический файл на 5000 строк.
* Ошибочные сценарии CLI: файл не найден, невозможно записать отчёт, неверные аргументы.

Ожидаемое покрытие `log_analyzer` (без `__main__`/`analyze.py`) — **≥ 95 %**.

## 7. Ограничения и примечания

* Время в журнале — строго UTC (`Z`, `+00:00`, `-00:00`). Ненулевые смещения отклоняются
  парсером — это соответствует требованию «timestamp в ISO 8601 UTC».
* В терминале показываются первые 50 повреждённых строк (далее «…and N more»);
  полный список — всегда в JSON/CSV.
* `top_error_codes` строится **только** по записям с `level == ERROR`.
* `filtered_events`, `by_level`, `by_source`, `top_error_codes` считаются по **отфильтрованным
  корректным** записям. `total_lines`, `valid_lines`, `invalid_lines` — глобальные, фильтрами
  не затрагиваются.
